# Architecture

Describes the system as it runs locally, and the temporary AWS deployment defined by the CDK stack in `infrastructure/` (see [AWS deployment (temporary)](#aws-deployment-temporary) and [AWS deployment status and roadmap](../README.md#aws-deployment-status-and-roadmap)). Statements here were checked against the code; file paths are given so they can be rechecked.

## Overview

```
Browser (POS / display / dashboard)  ──HTTP /api/v1──▶  Spring Boot API  ──JDBC──▶  PostgreSQL
        static files served by the same API process ◀──┘
```

One deployable unit: the API process also serves the three built web apps. The browser calls the API on the same origin, so there is no CORS configuration. In development, Vite serves the apps on `:5173` and proxies `/api` to `:8080` (`frontend/vite.config.ts`).

## Components

### Backend (`backend/`, package `com.counterline.pos`)

Java 21, Spring Boot 4.1, Maven wrapper. Organised by feature, each package holding its controllers, services, entities and repositories:

| Package | Responsibility |
| --- | --- |
| `auth` | PIN login, device set-up, manager approval, dashboard login, JWT issue/validation, login throttle, PIN locks, security rules |
| `catalog` | Items, categories, options/modifiers |
| `orders` | Checkout, order lifecycle (place, pay, void, refund), payments, receipts, promotions applied to a sale |
| `discounts`, `promotions`, `loyalty`, `vouchers` | Discount arithmetic, promotion rules, points and member entitlements, vouchers |
| `customers` | Members and phone-number handling |
| `display` | Customer-display pairing and its own restricted API, including `GET /api/v1/display/posters`: the closed set of poster keys for promotions that are active and run today in the configured business time zone (the seasonal one also needs a seasonal item on sale), with a `validUntil` of five minutes or the next midnight in that zone, whichever is first, sent `no-store`. The display owns the wording, shows only unexpired answers and otherwise shows neutral posters. |
| `register`, `timecards` | Cash register sessions, staff clock-in/out |
| `reports`, `dashboard` | Sales reports and the head-office/manager API |
| `outlet`, `staff` | Outlets and per-outlet staff |
| `common` | Error handling (RFC 9457 problem details), clock, static-asset caching |

### Frontend (`frontend/`)

React 19 + TypeScript, built by Vite from three HTML entry points: `index.html` (POS), `display.html` (customer display), `dashboard.html` (dashboard). Source is under `frontend/src/` (`features/` for POS screens, `dashboard/`, `display/`, shared `components/`, `lib/`, `api/`).

### Database

PostgreSQL 17. Schema is owned by Flyway (versioned migrations in `db/migration`, applied in order); Hibernate only validates (`ddl-auto: validate`). Under the `local` profile Flyway also loads repeatable sample data from `db/demo` (catalogue and outlets).

### Packaging

`Dockerfile` has three stages: build the web apps (Node 22), build the API with the built web apps copied into its static resources (JDK 21), then a JRE-only runtime image running as a non-root user with a health check on `/actuator/health`. `.dockerignore` is an allowlist (only `backend/` and `frontend/`). `docker-compose.yml` provides a development database and, under the `app` profile, the whole image with a separate database.

## AWS deployment (temporary)

Defined in `infrastructure/lib/infrastructure-stack.ts`; a reproducible, temporary, owner-run deployment, not a production design. This section describes what the stack defines; the repository provides no continuously hosted environment, and deployments are external, owner-managed and created on demand, so these docs cannot assert live external state. Deploy only for testing or demonstrations and destroy afterwards (see the [infrastructure guide](../infrastructure/README.md#teardown-and-cost)).

```
Owner (one IPv4 /32) ──HTTP :80──▶ ALB (public subnets) ──HTTP :8080──▶ Fargate task ──JDBC :5432──▶ RDS PostgreSQL
                                                                              │                     (isolated subnets)
                                                                              └─▶ Secrets Manager, ECR, CloudWatch Logs
```

**Network and trust boundaries**

- The VPC spans two AZs with public subnets and isolated database subnets. There is no NAT gateway.
- The load balancer's security group allows inbound TCP 80 only from the owner's IPv4 `/32` (the `AllowedIpv4Cidr` stack parameter) and outbound only to the application's security group on 8080. Traffic is plain HTTP; there is no TLS.
- The single Fargate task sits in a public subnet with a public IP, because there is no NAT for it to reach ECR, Secrets Manager and CloudWatch. Its security group accepts inbound traffic only from the load balancer on 8080.
- The database is in isolated subnets, not publicly accessible, with storage encryption. Its security group accepts inbound TCP 5432 only from the application's security group and allows no outbound traffic.

**Identity and secrets**

- The task execution role is generated by CDK from the container definition: it pulls the image, writes the log group and reads the referenced Secrets Manager secrets, which are injected as environment variables (database username and password, PIN pepper, JWT key).
- The application task role has no permission policies attached; the application makes no AWS API calls.
- Bootstrap is configured off in the stack (`POS_BOOTSTRAP_ENABLED=false`). See the README for enabling it for first run.

**Health and logs.** The load balancer checks `/actuator/health`; the ECS service rolls back a failed deployment through its circuit breaker. Application logs go to a CloudWatch log group with seven-day retention.

## Security model

- **Stateless bearer JWT**, HS256, signed with a configured secret; no cookies, so CSRF protection is disabled by design (`auth/SecurityConfig.java`).
- **Channels.** Each token carries a channel claim: till, dashboard, display, or single-action approval. Route rules require the right channel, so a dashboard session cannot use till-only endpoints, `/api/v1/dashboard/**` opens only to a dashboard login (email and password; a manager's PIN at the till gets 403), a display token opens only `/api/v1/display/**`, and an approval token is accepted only for the one operation it names (discount, void or refund), once.
- **Roles:** `STAFF`, `MANAGER` (till/dashboard) and `ADMIN` (head office). Catalogue, discount and voucher management is `ADMIN` only; other dashboard routes allow `ADMIN` or `MANAGER`.
- **Staff PINs** are six digits, hashed with a server-side pepper; passwords for the dashboard use BCrypt. Failed PIN attempts are counted per outlet PIN pad (or per client address where there is no pad); the 10th failure locks it for 5 minutes by default. The counts are stored in PostgreSQL, so every API instance sees them, and a dashboard user can unlock a pad.
- **Public routes:** login/set-up endpoints, the outlet list, health and the static web apps.
- **API documentation is local-only.** The OpenAPI document and Swagger UI are enabled by the `local` profile and off in every other (`springdoc.*.enabled` in `application.yml`), where their URLs answer 404 like any unknown path. The application refuses to start if either is enabled outside `local` (`common/ApiDocsLocalOnly.java`).
- **Response headers.** Every response (the web apps, static files and the API) carries a `Content-Security-Policy` limited to the application's own origin, with scripts from `'self'` only (no inline or eval'd script) and no `'unsafe-inline'` for styles either: React sets its `style` values through the CSSOM, which `style-src 'self'` allows. `data:` is allowed for images only (one inline SVG icon in the stylesheet); fonts and everything else come from the origin. `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff` and `X-Frame-Options: DENY` accompany it. There is no `Strict-Transport-Security` header yet: it waits for HTTPS. Under `local`, Swagger UI's own paths get a slightly looser policy (its page needs one inline style element); the apps keep the strict one (`auth/SecurityConfig.java`).
- Secrets have no defaults outside the `local` profile.

## Design decisions

- **Single image, same origin.** Simplest thing to run and deploy; avoids CORS and a separate static host. Cost: web and API releases are coupled.
- **Money is `BigDecimal` in the backend and API** (`SaleOrder`, decimal prices in JSON); rounding rules are in `discounts` and covered by unit tests. The frontend converts to **integer sen** at the boundary (`frontend/src/lib/money.ts`) to avoid floating-point drift when summing, and back to decimals for display and requests.
- **Idempotent payment.** Paying an order is keyed by a client request id, so a retried request returns the already-paid order instead of charging twice (`CheckoutService`).
- **Register cash.** A register is opened with an explicitly declared opening float (default RM0.00, fixed once the register is open; corrections are pay-ins or pay-outs; nothing carries over from the previous session). Expected cash = opening float + cash collected − cash refunded + pay-ins − pay-outs, where cash is the payments of methods of kind `CASH`, counted over the session as the sales report counts them (a sale when it was paid, a refund when it was made); card and other payments never raise it (`register/RegisterService.java`). A pay-out larger than the expected cash is refused with a 409 that states the available amount. Every drawer event (a payment, a refund, a pay-in or a pay-out) takes the outlet's open session row with an `UPDATE` that also advances its version, always after the sale's and the member's locks, and a register close locks the same row (placing an order only reads it `FOR SHARE`). Each event therefore either commits before a close and is counted by it, or waits and then finds the register closed and is refused; the pay-out ceiling is checked and the movement recorded under that lock, so concurrent pay-outs cannot spend the same cash. A payment's, refund's or movement's time is read only after the lock is held, so it cannot be dated into a session that closed while it waited. A close request names both the session id and the version the screen showed (`CloseRequest`); a session opened since, or any drawer event since that view, makes it stale (409) and the till reloads the register before it can be closed again. Refunds are never refused for the drawer's sake: they are owed and need a manager, so expected cash can go below zero and is shown as such, but they need an open register and belong to the session they are made in. This is a bookkeeping safeguard, not a fraud control: there is no maximum float. Sessions are windowed by the application's timestamps (opened, paid, refunded, closed), so instances are assumed to keep reasonably synchronised clocks.
- **Concurrency.** Orders, customers, register sessions, staff and outlets use optimistic locking (`@Version`); loyalty accounts, member entitlements and display records are read with pessimistic write locks where races would corrupt balances or counters. A stale staff or outlet edit (including one that would undo a deactivation, PIN reset or session revocation) fails with a 409; the bulk session revocation when an outlet closes also raises each staff row's version. Outlet and staff changes lock the outlet row first (lowest id first when two are involved; shared to join, open a register or clock in, exclusive to deactivate it or to remove its manager), then the staff row, so they serialize without deadlocking. Outlet names are unique ignoring case in the database.
- **An open outlet keeps a manager.** The last active manager of an active outlet cannot be deactivated, demoted or moved away (409), so the outlet can always set up its till and approve voids and refunds. A deactivated outlet is not held to it, and reactivating an outlet never needs a manager, so a closed outlet can always be wound down and recovered (add or reactivate a manager afterwards).
- **Sensitive actions need a manager.** A manager PIN entered at the till (`/auth/special-access`, which requires an `operation`: `DISCOUNT`, `VOID` or `REFUND`) yields a short-lived (5 minute default) approval token carrying that operation. Only that operation accepts it, and only once: used token ids are recorded in PostgreSQL (`used_approval_token`). A token with a missing, unknown or different operation is refused with the same generic answer and is not used up. It is used in two ways that differ:
  - **Void and refund** accept the token as a bearer credential and record it at once, so two racing requests cannot both succeed. A signed-in manager can also void or refund directly.
  - **Checkout discount approval** (department comps) sends the token in the request body (`approvalToken`), for checkout or for paying an edited order. It is checked for signature, expiry, the approval channel and the `DISCOUNT` operation, for the manager's current session (the same check as a bearer token: a PIN, role, outlet or login change, deactivation or a closed outlet ends it), and that its subject is an active manager at the paying staff member's outlet (`auth/ManagerApproval.java`). It is recorded inside the sale's own transaction: one approval authorises one completed sale, whatever its comped lines; a sale that fails leaves it unused; two sales racing for it cannot both commit. Retrying a completed request (same client request id) returns the sale without needing the approval again. A signed-in manager needs no token.
- **Reports are accounted by event time.** A sale counts on the day it was paid (`closedAt`, which is also the date on its receipt); a refund counts on the day it was made. A zero-total sale can be refunded once, as a refund of nothing, which gives back its voucher and points.
- **Points expire 365 days after the latest purchase.** Positive points expire 365 days (of 24 hours) after the member's latest completed, unrefunded purchase at any outlet (`sale_order` closed and not refunded). Every such purchase starts the year again, also one that earns 0 points or redeems points; manual adjustments, refunds and reversals and every other ledger entry never do, and a placed order only counts once it is paid. Refunding the latest purchase counts from the one before it, and a member with no completed, unrefunded purchase has no expiry (`expiresAt` is null). At the expiry instant itself the points are already gone. Only a positive balance expires: a debt and a zero balance never do. Nothing is stored for the date; it follows from the sales. Expiry is recorded lazily, under the loyalty-account lock, whenever the account is locked for a sale, a refund or an adjustment or its history is read: the balance goes to zero and one `EXPIRE` ledger entry (negative, tied to no sale or staff member) is written in the same transaction, dated at the expiry instant but never before an entry already on the history (a refund can move the expiry back to a moment long past). A purchase expires points that ran out before it is paid, then earns on the clean balance. Reads that cannot write (the cart's quote and a member's perks) show points that have run out of time as zero without recording anything. The date is exposed as `expiresAt` in the quote's loyalty preview (a year from the sale being quoted), `pointsExpireAt` in the member perks and `expiresAt` in the dashboard points history; the printed Loyalty Points report is per outlet and sale-based, so expiry (a chain-wide event) is not in it. Migration V29 stores nothing for existing accounts: their expiry follows from their existing sales, so points whose latest purchase is more than a year old expire the first time the account is touched.
- **Points can go negative, only through a refund.** A refund takes back every point its sale earned, also those the member has spent since, and gives back those the sale redeemed. The balance may then be below zero: the member owes the points, later purchases earn them back first, and the dashboard and the cart say so. Spending points (a redemption) and a manual take-away still need the points to be there, so nothing else can make a balance negative; a member in debt can still be given points by an adjustment.
- **A placed order is judged as of when it was placed.** An order stores the instant its promotions' time rules are read at (when it was placed, or last edited) and, per line, whether the item's folder counted towards promotions and whether the item was a seasonal flavour. Paying later uses these: promotion dates, the birth month (in the configured business time zone), the registration reward's 24 hours and seasonal windows give the same answer as at placement, whatever has changed since. Two things are always read as they are at payment, so nothing is spent twice: the member's points, and the once-only rewards (Registration and Google Review), which count only paid, unrefunded orders. Promotions switched off since (\`active\`) stop an order being paid.
- **Net and gross reports.** The Sales Summary, Payment Methods and Hourly Sales are net of refunds. The rankings of what was sold or given (Item Sales, Category Sales, Discounts, Modifiers, and the dashboard's busiest hours, top items, sales by folder, free items and discounts) are gross activity before refunds: a refunded sale stays in them, and the screens say so.
- **One business time zone for every outlet.** `POS_OUTLET_TIME_ZONE` (`pos.outlet.time-zone`) names the single time zone shared by all outlets; outlets have no time-zone setting of their own. It sets report day boundaries, receipt dates, promotion and seasonal dates, the birth month, the display posters' day and timecard corrections' local times.
- **Errors are problem details** for both application and security failures, so clients handle one shape.
- **Behind a proxy.** `forward-headers-strategy: native` lets login throttling see the real client address when a load balancer is in front.
- **Sessions end.** Every staff and head-office token carries an authentication session version checked against the database on every request (a deactivation, role or outlet change, new PIN or password, changed login, outlet closure or, for a till or approval token, the iPad's reset raises it and ends all that person's earlier tokens, which stay dead if the change is undone). Logging out (`POST /api/v1/auth/logout`, `POST /api/v1/dashboard/auth/logout`) ends only the token presented, recording its id in `revoked_token` until it would have expired anyway; the person's other sessions go on.
- **Login throttling admits before it checks.** Each guess (password, PIN, set-up PIN, pairing code) is admitted by one atomic statement per throttle key *before* it is checked, counted as under way, so a burst of parallel guesses can never get more than the limit's worth past it: while a key's failures and attempts under way add up to its limit, the rest get 429. A wrong guess then counts as a failure (the limit-th locks the key for the window); a right one gives its place back, so a success never clears anyone's failures. The keys: an outlet's PIN pad (per outlet, not per client), the dashboard account on one client (the limit), the client address (5 times the limit), the account on all clients (10 times the limit: one client cannot lock the real user out elsewhere), the pairing code per client address and across all clients (10 times the limit; the lock answers alike for right and wrong codes). A display takes at most 5 member sign-ups per window (counted atomically; one the application refuses, such as a conflict or an invalid field, is given back, while one that fails in the database or its transaction stays counted because it is not known whether the member was made). The throttle uses plain autocommit statements and refuses to run inside a transaction, so recording a failure never needs a second database connection while the request holds one (a burst of failed logins cannot run the pool dry) and a failed request does not roll its own failure back; the login, set-up, pairing, clock and display-member paths therefore run outside transactions and open their own short ones. **The throttle fails closed.** A counting statement that fails (a database error, a dropped connection) is never retried or undone, since it is not known whether it was applied and a second try could take the place of another attempt; every key of an attempt is still tried once, and the original error is the one thrown, with the others attached. A place left counted this way, or by a process that died mid-attempt, only makes that key a little stricter, and is forgotten once a throttle window passes with no attempt admitted on the key (each admission stamps `pending_at`; the failures' own window is not moved by admissions). Until then it is not cleared by anything else: **unlocking a PIN pad from the dashboard clears its failures and the lock but keeps the attempts under way**, so an in-flight attempt never loses its place to a recreated row, and a leaked place survives an unlock until the quiet window passes.
- **Catalogue edits are version-checked.** Tabs, folders, items, option groups and options each carry a `version` (V32, `@Version`). The dashboard lists it with every row and an edit must send back the version it was loaded at; an edit made from an older copy (another admin saved, or the row was reordered, since) is refused with the usual 409 "Changed elsewhere. Reload." and nothing is written, and the dashboard then reloads the row from the newer version. An edit that names no version is a 400. A reorder carries the version of every row of the list it was made from (`ids` plus `versions`): a list with a row saved or moved since is the same 409, one missing a row is a 400, and the dashboard reloads after either. Only the rows whose place changes are written (so only their versions move), and a request for the order the rows already have writes nothing. Changes still happen one at a time under the catalogue lock; the version is what stops the later of two full-form saves from silently putting back a field the earlier one changed.
- **Clock events are consistent per person.** Clock In/Out checks the PIN before its transaction, then locks the person's row and checks again that they are still active, still this outlet's staff and still have the PIN that was checked (a deactivation, a move or a PIN reset takes the same lock), so a clock-in that waited for one is refused as a wrong PIN and records nothing. Whether someone is clocked in is decided by their latest event **by id** (the order events were recorded in) in every query, never by the time on the event, and every new event is dated by the **database's clock** (`clock_timestamp()`, read once the person's row is locked), the one clock all API servers share. A previous event dated ahead of it (a bad clock or import) changes nothing: it is logged as a warning, its time is never copied, and the person clocks as normal, so nobody is locked out. A dashboard correction takes the clock-out as a wall-clock time (`outAtLocal`) read in the business time zone (the timecards report names it), never the browser's; it is judged (exactly one time given, and a local time the zone skipped or repeats is refused) before anything is locked. In a zone with daylight saving (the default zone has none) the dashboard therefore cannot select between the two instants of the repeated hour; that clock-out is entered through the API with the exact instant (`outAt`). A correction only ever looks at an open shift at the outlet it is asked for: anyone else, or nobody, is the same 409, so it cannot be used to find out who works where. A staff edit carries the `version` it was loaded at, like the catalogue: an older form is the same 409 and writes nothing.
- **Dashboard changes name who made them.** Every staff change (create, edit, PIN reset, dashboard-login change or removal, deactivate, reactivate) adds a row to `staff_audit` in the same transaction: the actor's type and stable id taken from the token, the person changed, the action and the database time. Staff administration is head-office-only (`/api/v1/dashboard/admin/**` requires the `ADMIN` role), so today every row records `ADMIN` and the head-office account id; the log's constraint also allows `MANAGER`, but no current route writes it. It is append-only (a trigger refuses any update or delete) and holds no PIN, password, hash or e-mail; a refused change or one that changes nothing writes no row. A timecard correction, which head office may make for any outlet and a manager for their own, stores the same type and id (`corrected_by_type`, `corrected_by_id`) beside `corrected_by`, which stays the name to show in reports as it was then; a manager is recorded as `MANAGER` with their staff id. A token whose subject is not an account id is refused (401) rather than recorded under a guess. Corrections made before V35 only ever kept a name, so they are marked `LEGACY` with no id; their identity is not reconstructed from the name, which is neither unique nor stable. A constraint keeps the three columns consistent (`LEGACY` has no id, `ADMIN` and `MANAGER` always have one).
- **Operational endpoints.** Only `health` and `info` are exposed by Actuator.
